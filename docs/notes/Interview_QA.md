## 1. 아키텍처 선택

### Q1. 예매 경로에 분산 락을 쓰지 않은 이유는?

**의도** — README 를 읽고 "락으로 동시성 제어"를 기대한 면접관이 코드를 열어보고 묻는다. 대안을 비교해 고른 것인지 확인.

**모범 답변**
> 경합을 락으로 직렬화하는 대신 **원자적 선점 지점 하나**로 승자를 가렸습니다. Redis Set `avail:{scheduleId}` 에서 직접 선택은 `SREM`, 자동 배정은 `SPOP` 을 쓰는데, Redis 가 단일 스레드라 `SREM` 이 1 을 반환하는 요청은 정확히 하나입니다. 이긴 요청만 DB 로 내려가고, DB 의 `@Version` 낙관락과 좌석당 활성 예약 1건 유니크 제약(`uk_active_seat`)이 최종 방어선입니다.
> 락 방식도 PoC(`LockBookingService`)로 만들어 비교했는데, 스케줄 단위 락이라 서로 다른 좌석 예매까지 직렬화되고 획득·해제 왕복이 붙습니다. 선점은 Redis 명령 1회로 패배자를 즉시 반려합니다. Redisson 은 조회 캐시의 single-flight 에서만 실제로 씁니다.

**꼬리 질문**
- "락 단위를 좌석으로 줄이면요?" → 좌석 락이면 직렬화 문제는 줄지만, 여전히 패배자가 락 대기·왕복 비용을 낸다. 선점은 대기 자체가 없다. 단, **두 방식의 처리량을 같은 조건에서 측정한 수치는 없다**(E6 백로그) — 설계 판단이라고 명확히 말한다.
- "SEAT 와 AUTO 가 같은 좌석을 동시에 노리면?" → 같은 Set 을 공유하므로 `SREM` 과 `SPOP` 중 하나만 그 원소를 가져간다.

**근거** — `booking/BookingService.java`, `booking/LockBookingService.java`, `booking/RedisSetPreemption.java`

### Q2. 메시지 큐는 왜 안 썼나? 예매를 큐로 받으면 피크를 더 잘 흡수하지 않나?

**의도** — Redis 동기 vs MQ 비동기 트레이드오프 이해.

**모범 답변**
> 큐로 받으면 피크 흡수는 쉽지만 사용자는 "접수됨"만 받고 결과를 폴링해야 합니다. KTX 예매의 본질 난제는 같은 좌석 동시 점유 제어라서, 요청-응답 안에서 경합을 직접 제어하는 쪽을 택했습니다. 피크 흡수는 큐 대신 **입장 제어(활성 세션 상한 K + 429)**로 했습니다. MQ 는 결제 결과·통계 같은 비동기 사이드로 범위를 한정하기로 결정했고, 이번 범위에서는 구현하지 않았습니다(P5 Could). HELD 만료도 큐가 아니라 DB 기준 스케줄러 sweep 으로 처리합니다.

**꼬리 질문**
- "큐 방식의 정합성은 어떻게 보장하나?" → 스케줄(또는 좌석) 단위 파티션으로 직렬화하면 소비자 내부에서 경합이 사라진다. 대신 멱등 소비·재처리·결과 통지 경로가 필요하다.

**근거** — README "아키텍처 결정", `docs/KTX_Ticketing_Architecture_and_Verification_Goals.md`

### Q3. 2-tier 일관성 모델이란?

**모범 답변**
> 조회/표시(운행 리스트·잔여석·매진)는 빠른 **약한 일관성**(staleness ≤ 2s), 예매 확정은 DB 트랜잭션 안에서만 결정되는 **강한 일관성**으로 분리했습니다. 잔여석을 DB 강한 일관성으로 묶으면 매 조회가 재고를 집계해 조회 p95 가 8~9초까지 무너졌습니다(E3 Before). 그래서 "화면마다 잔여석이 다르게 보이는" 것은 버그가 아니라 의도한 트레이드오프이고, 그 경계를 SLO(S2b staleness ≤ 2s / S4 oversell 0)로 측정 가능하게 했습니다.

**⚠ 주의** — 잔여석은 별도 카운터가 아니라 `SCARD avail` 파생값이다. 시퀀스 다이어그램의 "잔여 -1 동기화"는 실제 코드와 다르다(면접 전 수정 권장).

## 2. 동시성 · 정합성

### Q4. 1,000명이 같은 좌석을 노릴 때 정확히 1명만 성공한다는 걸 어떻게 보장하고 증명했나?

**모범 답변**
> 보장은 이중 방어선입니다. 1차는 Redis `SREM` 원자 선점 — 999명이 DB 앞에서 409 로 반려됩니다. 2차는 DB `@Version` 과 `uk_active_seat` 입니다.
> 증명은 L1 시나리오로 했습니다. 단일 좌석에 1,000 VU 를 동시에 보내 성공 1건, 부하 전 `SCARD` 1000 → 부하 후 999, DB 는 HELD 1·중복 0·AVAILABLE 999 로 **애플리케이션 응답과 DB·Redis 사후 상태를 교차 검증**했고 3회 반복해 일관됐습니다. `/internal/consistency` 감사 엔드포인트가 부하 teardown 에서 자동으로 이 검증을 수행합니다.

**꼬리 질문**
- "진짜 1,000 동시였나?" → Q21.

**근거** — README "실측 증거" 4장, `booking/reconcile/ConsistencyAuditService.java`

### Q5. E1 에서 선점을 꺼도 oversell 이 0 이었다면 Redis 는 왜 필요한가?

**의도** — 거의 반드시 나온다. "정직한 결론"을 본인이 이해했는지.

**모범 답변**
> 맞습니다, 정확성은 DB 만으로도 지켜집니다. 선점의 값은 **정확성이 아니라 비용**입니다. 선점이 없으면 1,000건이 전부 DB 커넥션을 잡고 낙관락 충돌로 실패합니다. 선점을 켜면 패배 999건이 Redis 에서 끝나 reserve 중앙값이 약 1.2s → 0.29s 로 약 4배 줄었습니다.
> 좌석 하나가 아니라 인기 열차 전체에서 동시에 경합이 일어나면 DB 커넥션 풀(10개)이 먼저 고갈되므로, Redis 는 DB 를 보호하는 앞단 게이트입니다.

**꼬리 질문**
- "그럼 E1 After 의 availDrift=0 / Before=1 은?" → 선점을 끄면 `SREM` 을 안 하니 DB 는 HELD 인데 Set 에 좌석이 남는다(stale 1). reconcile 이 수렴시키는 대상이다.

### Q6. `SREM` 은 성공했는데 DB 쓰기가 롤백되면? 둘이 원자적이지 않다.

**모범 답변**
> 그 좌석은 Redis 에는 없고 DB 에는 AVAILABLE 인 **missing** 상태가 됩니다. 이건 일시적 언더셀이지 오버셀이 아닙니다. 60초 주기 reconcile 이 DB 를 기준으로 되돌립니다.
> 방향이 비대칭인 게 핵심입니다. Redis 에만 남은 **stale** 좌석 제거는 최악이 언더셀이라 언제나 안전합니다. 반대로 missing 좌석을 `SADD` 로 되살리는 건 위험합니다 — 지금 막 선점돼 커밋 직전인 좌석을 되살리면 오버셀이니까요. 그래서 선점할 때 Lua 스크립트로 `SREM` 과 함께 "마지막 선점 시각"을 원자 기록하고, 그 시각이 grace(5분) 이내면 건너뜁니다.

**꼬리 질문**
- "그 좌석은 최대 얼마나 못 팔리나?" → grace 5분 + reconcile 주기 60초 ≈ 최대 6분.
- "Lua 로 Redis+DB 를 묶거나 2PC 는?" → Redis 와 MySQL 은 공통 트랜잭션이 없다. DB 를 SoT 로 두고 사후 수렴시키는 것이 비용 대비 합리적이라고 판단했다.

**근거** — `booking/reconcile/ReconciliationService.java`, `docs/KTX_Ticketing_Reconcile_Design.md`

### Q7. Redis failover 로 최근 `SREM` 이 유실되면?

**모범 답변**
> 복제가 비동기라 failover 직전의 `SREM` 이 사라지면 같은 좌석의 승자가 둘 생길 수 있습니다. 이때 두 번째 승자는 첫 번째가 이미 커밋한 **최신 version 을 읽기 때문에 `@Version` 으로는 막히지 않습니다**. 막는 건 `uk_active_seat` 입니다 — 같은 좌석에 활성 예약을 하나 더 INSERT 하려다 유니크 위반으로 롤백되고 409 로 변환됩니다. "정확성은 DB 가 보장하고, 성능은 앞단 게이트가 맡는다"는 구조라 Redis 가 틀려도 오버셀은 생기지 않습니다.

### Q8. 낙관락을 고른 이유는? 핫 좌석은 비관락이 정석 아닌가?

**모범 답변**
> 경합은 Redis 가 먼저 걸러내서 DB 까지 오는 충돌이 드뭅니다. 충돌이 드문 환경에선 낙관락이 맞습니다. 비관락(`SELECT … FOR UPDATE`)은 패배자까지 행 락을 기다리며 커넥션을 붙잡아, 이 시스템의 병목인 DB 커넥션 점유시간을 늘립니다.

### Q9. `uk_active_seat` 는 어떻게 구현했나?

**의도** — MySQL 제약을 알고 실제 버그를 겪었는지.

**모범 답변**
> 처음엔 `reservation.seat_inventory_id` 에 전역 유니크를 걸었는데, 취소·만료는 행을 지우지 않고 상태만 바꾸니 되돌아온 좌석을 다시 예매하면 Duplicate entry 로 500 이 났습니다. L4 부하 테스트에서 발견했습니다(B-2).
> 의도한 불변식은 "한 좌석에 동시에 활성(HELD/CONFIRMED)인 예약은 1건"입니다. PostgreSQL 이면 부분 인덱스(`WHERE status IN …`)로 끝나지만 MySQL 은 지원하지 않아서, 활성일 때만 `seat_inventory_id` 를 갖고 아니면 NULL 인 **STORED 생성 컬럼**을 만들고 그 위에 유니크를 걸었습니다. MySQL 유니크는 NULL 중복을 허용하므로 과거 예약은 공존합니다.

**꼬리 질문**
- "약점은?" → **활성 상태 목록이 DDL 에 하드코딩**돼 있다. 나중에 `PAYMENT_PENDING` 같은 활성 상태를 추가하면서 마이그레이션을 빠뜨리면 방어선에 조용히 구멍이 난다. 먼저 말하면 가점.
- "`SeatInventory` 의 `@Version` 이 이미 막는데 유니크가 꼭 필요한가?" → 필요하다. 둘이 막는 경우가 다르다. `@Version` 은 **같은 순간에 같은 버전을 읽은 동시 쓰기**만 막는다. Redis 에 stale 좌석이 남아 있거나 failover 로 `SREM` 이 유실돼 "이미 팔린 좌석"을 뒤늦게 선점한 요청은 최신 버전을 읽으므로 `@Version` 을 통과한다. 게다가 `SeatInventory.markHeld()` 는 현재 상태를 검사하지 않는다. 이 순차적 stale 경우를 막는 건 `uk_active_seat` 뿐이다(Q7).

**근거** — `src/main/resources/db/migration/V2__active_seat_unique.sql`, `docs/plans/Seat_Rebooking_Unique_Constraint_Fix_Plan.md`

### Q10. 그냥 취소·만료 시 행을 삭제하면 더 단순하지 않나?

**모범 답변**
> 제약만 보면 단순해집니다. 남는 행이 항상 활성이니 일반 유니크면 되죠. 실제로 검토했다가 기각했습니다.
> 첫째, `CANCELLED` 와 `EXPIRED` 는 도메인에서 다른 사건인데 둘 다 "행 없음"으로 뭉개져 상태 머신 절반이 사라집니다. 둘째, 고객 문의·환불 근거·취소율 통계의 원천이 없어집니다. 셋째, 지금은 이중 취소를 상태 재확인으로 no-op 처리하는데, 삭제 방식이면 재시도한 클라이언트가 404 를 받아 "이미 취소됨"과 "없는 예약"을 구분할 수 없습니다.
> 규모가 커지면 삭제가 아니라 **활성/이력 테이블 분리**가 맞다고 봅니다. 취소 시 같은 트랜잭션에서 이력 테이블로 옮기고 원본을 지우면, 활성 테이블엔 단순 유니크를 쓰면서 이력도 남습니다. 대가는 쓰기 2회와 "내 예약 목록" 조회 시 UNION 입니다.

### Q11. Redis 부수효과를 왜 커밋 후에 실행하나?

**모범 답변**
> 커밋 전에 `SADD`(좌석 반환)나 `DECR`(슬롯 반환)을 하고 트랜잭션이 롤백되면, DB 는 HELD 인데 Redis 는 가용 상태가 됩니다. 그게 오버셀·과다 입장으로 가는 경로입니다. 그래서 DB 전이는 별도 빈(`ReservationLifecycleTransactionHelper`)의 트랜잭션 안에서 끝내고, 실제 전이가 일어났을 때만 식별자를 돌려받아 커밋 후에 부수효과를 실행합니다. 이중 취소·확정도 식별자가 비어 있으면 아무것도 안 하므로 자연히 흡수됩니다.

**꼬리 질문**
- "`TransactionSynchronization.afterCommit` 은?" → 가능하다. 헬퍼 빈 분리를 택한 건 트랜잭션 경계가 메서드 시그니처로 드러나고 테스트가 쉬워서다. 같은 클래스 안에서 `@Transactional` 메서드를 호출하면 프록시를 거치지 않는 문제(self-invocation)도 피한다.
- "커밋 후 Redis 호출이 실패하면?" → DB 는 이미 커밋돼 있고 Redis 만 어긋난다. `SADD` 실패는 missing → reconcile 이 수렴, `DECR` 실패는 슬롯 누수(Q14 와 같은 문제).

**근거** — `booking/ReservationLifecycleService.java`

## 3. 입장 제어

### Q12. K=100 은 어떻게 정했나?

**모범 답변**
> 감으로 정하지 않고 L5b 임계점 탐색으로 역산했습니다. 예매 경로만 격리해 50→100→150→200→300 TPS 계단으로 올리니, 150 까지는 목표를 그대로 추종하고 200 에서 VU 가 폭증하며 약 183, 300 에서 약 189 로 평탄해졌습니다. 그래서 안전 처리량 150, 천장 189 로 보고, 리틀의 법칙 L = λ × W 에 W ≈ 0.9s, 마진 0.75 를 곱해 150 × 0.9 × 0.75 ≈ 100 을 얻었습니다.

**꼬리 질문**
- "스케줄당 K 면 스케줄 50개일 때 전역 5,000 아닌가?" → 맞다. 병목은 전역(DB 풀)인데 K 는 스케줄당이라 부하가 여러 스케줄에 고르게 퍼지면 보호가 뚫린다. 실전은 소수 인기 노선 쏠림이라 "동시 인기 스케줄 1개"를 보수적으로 가정했고, 전역 K(`active:global`)를 AND 조건으로 얹는 설계를 후속 과제(T4-14)로 남겼다.

**근거** — `docs/plans/Admission_K_Calibration_Plan.md`, `P4_Result.md` T4-7

### Q13. ⚠ W=0.9s 는 사용자가 생각하는 시간이 없는 부하 루프의 값 아닌가?

**의도** — K 산정을 깊게 읽은 면접관의 질문. 본인이 먼저 인지해둘 한계.

**모범 답변**
> 맞습니다, 한계입니다. 측정 루프는 입장 → 예매 → 즉시 확정이라 W 가 0.9초였지만, 실제 슬롯은 입장부터 확정·취소·만료까지 점유됩니다. 사람은 수십 초에서 HELD TTL 5분까지 걸리니, 같은 K=100 이면 실제 처리량은 측정치보다 훨씬 낮아집니다.
> 근본 원인은 **DB 를 보호하는 "동시 처리 중 요청 수"와 "열려 있는 사용자 세션 수"를 카운터 하나로 겸한 것**입니다. 개선한다면 둘을 분리하겠습니다 — DB 보호는 예매 API 의 in-flight 동시성 제한으로, 세션 상한은 실제 사용자 W 로 다시 역산한 별도 값으로 둡니다.

### Q14. ⚠ 토큰만 받고 예매를 안 하면 슬롯은 언제 반환되나?

**의도** — 코드를 읽는 면접관이면 찾는다.

**모범 답변**
> 현재는 반환되지 않습니다. 알고 있는 결함(B-3)입니다. 슬롯 반환(`leave`)은 예약의 확정·취소·만료에서만 호출되는데, 활성 카운터(`active:{id}`)와 토큰(`entry:{token}`)이 서로 다른 키라 토큰이 TTL 로 사라져도 카운터는 그대로입니다. 예매가 409/410 으로 실패하거나 사용자가 이탈해도 마찬가지라, 시간이 지나면 K 가 조기에 포화됩니다.
> 고친다면 카운터를 ZSET 으로 바꾸겠습니다. 멤버는 토큰, score 는 만료 시각으로 두고, 입장 시 `ZREMRANGEBYSCORE` 로 만료분을 지운 뒤 `ZCARD` 로 센 다음 `ZADD` 하는 걸 Lua 로 묶으면, 토큰 수명과 슬롯이 자동으로 같이 움직입니다.

**꼬리 질문**
- "Redis keyspace notification 으로 만료 이벤트를 받으면?" → 전달 보장이 없는 fire-and-forget 이라 누락 시 영구 누수가 된다. 카운터 자체를 만료 가능한 자료구조로 바꾸는 게 맞다.

**근거** — `admission/AdmissionService.java`, `docs/KTX_Ticketing_Task_Checklist.md` B-3

### Q15. INCR 후 DECR 롤백 방식에 race 는 없나?

**모범 답변**
> 검사 후 증가(GET → 비교 → INCR)는 race 가 있어서, INCR 의 **반환값으로 판정**합니다. 넘었으면 즉시 DECR 합니다. 순간적으로 카운터가 K 를 넘어 경계 근처 요청이 실제론 자리가 있는데 거절될 수는 있지만, **K 를 넘는 입장은 일어나지 않습니다**. 입장 제어는 보호가 목적이라 이 근사로 충분하고, Lua 원자화는 하지 않았습니다.

### Q16. ⚠ 같은 사용자가 `/api/entry` 를 100번 호출하면?

**모범 답변**
> 지금은 호출마다 슬롯 하나를 쓰고 새 토큰을 받습니다. userId 도 요청 본문에서 받습니다. 인증·인가를 범위 밖으로 둔 결정의 결과입니다(동시성·정합성이 평가 핵심이라 부하 테스트를 단순하게 유지). 실서비스라면 인증된 사용자 기준으로 (scheduleId, userId) 당 토큰 1개로 제한해 재호출 시 기존 토큰을 돌려주겠습니다.
> 대신 예매 단계에서는 userId·scheduleId 를 본문이 아니라 **토큰에서만** 꺼내서, 남의 세션으로 예매하는 위변조는 막아두었습니다.

### Q17. 보이는 대기열 대신 429 를 택한 이유는? UX 가 나쁘지 않나?

**모범 답변**
> 실제 KTX 앱이 순번을 보여주지 않는 방식이라 도메인에 충실하고, 대기 순번 엔티티와 순번 관리 비용이 없습니다. 트레이드오프는 공정성입니다. 먼저 온 사람이 먼저 들어간다는 보장이 없고, 클라이언트가 동시에 재시도하면 재시도 폭주가 생길 수 있습니다. 그래서 `Retry-After`(5초)를 주는데, 실서비스라면 클라이언트 쪽에 지터를 넣어 재시도 시점을 분산시키겠습니다.
> E2 에서 효과를 측정했습니다. 입장 제어를 끄면 p95 22초·미처리 38k·VU 2,000 팽창으로 무경계 열화했고, 켜면 초과분 85.4% 를 429 로 흡수하면서 reserve p95 가 약 28ms 로 유지됐습니다.

## 4. 조회 · 캐시

### Q18. 조회 경로를 어떻게 최적화했나?

**의도** — "측정 후 최적화"를 실제로 했는지.

**모범 답변**
> L3 조회 폭주에서 약 850 TPS 에 p95 8~9초로 포화됐습니다. 먼저 DB 풀을 늘려봤는데 지렛대가 아니었습니다. MySQL 이 2코어라 풀을 키우면 커넥션 점유시간이 오히려 늘었습니다(tx 안 6.9 → 26.4ms). 진짜 지렛대는 **점유시간**이어서, 잔여석 `SCARD` 를 트랜잭션 밖으로 빼 커넥션이 Redis 왕복을 감싸지 않게 했고, 최종적으로 Redis 공유 단기 캐시(TTL 1s)로 히트 시 DB 를 아예 안 타게 했습니다. 결과는 2,497 TPS·p95 26ms 입니다(E3). 각 최적화는 설정 토글로 켜고 꺼서 개별 효과를 따로 측정했습니다.

### Q19. 캐시 stampede 는 어떻게 막았나? 한계는?

**모범 답변**
> 핫키 TTL 이 만료되는 순간 요청이 몰려 일제히 DB 로 가는 걸 single-flight 로 막았습니다. 미스면 키 단위 분산 락을 잡고, 락 안에서 캐시를 **한 번 더 확인**합니다. 먼저 들어간 요청이 채웠으면 그걸 쓰고, 아니면 한 번만 계산해 넣습니다. 로컬 캐시(Caffeine)가 아니라 Redis 공유 캐시인 이유는 멀티 인스턴스에서 인스턴스마다 표시가 달라지지 않게 하려는 것입니다.
> 한계는 히트율입니다. `from` 을 50개로 분산한 저히트율 다중 키(L3b)에선 캐시만으로 SLO 를 보장하지 못하고 DB 풀 병목이 돌아왔습니다. 또 여러 키가 동시에 채워져 동시에 만료되는 파도를 줄이려고 TTL 지터 옵션을 두었습니다.

**꼬리 질문**
- "락 대기가 타임아웃되면?" → 락 없이 직접 계산으로 폴백한다. 그 경우 일부 stampede 가 남지만 정확성은 그대로다.
- ⚠ "캐시 키에 `from` 이 원본 그대로 들어가는데?" → 클라이언트가 현재 시각을 초 단위로 보내면 키가 매번 달라져 히트율이 0 에 가까워진다. 분/날짜 단위로 내림하는 정규화가 필요하다.

**근거** — `schedule/ScheduleListCache.java`, `schedule/ScheduleQueryService.java`

### Q20. 매진을 보수적으로 표시한다면서, 캐시 TTL 동안 매진 편이 "잔여 있음"으로 보일 수 있지 않나?

**모범 답변**
> 네, 최대 TTL(1초, 지터 포함 시 약간 더) 동안 보일 수 있습니다. 그 사용자가 예매를 시도하면 `SREM` 이 0 을 반환해 즉시 교정되고, 예매 경로는 캐시를 타지 않아 오버셀과는 무관합니다. 정확히 말하면 "표시는 TTL 만큼 늦을 수 있고, 판정은 늦지 않는다"입니다.

## 5. 부하 테스트 신뢰성

### Q21. 1,000 VU 가 정말 동시였다는 건 어떻게 확인했나?

**모범 답변**
> 처음엔 1,000 VU 중 상당수가 `connection refused` 로 떨어져서(631건) 실제로는 1,000 동시가 아니었습니다. 앱 문제라고 단정하지 않고 가설별로 격리 실험을 했더니, 원인은 앱이나 Tomcat 이 아니라 Windows Docker Desktop 의 포트 프록시(NAT) 구간에 쌓이는 클라이언트 측 TIME_WAIT 압박이었습니다. k6 를 앱과 같은 Docker 네트워크에 두고 직결해 NAT 구간 자체를 없앴고, 이후 `http_reqs=2000`(1,000명 × 입장+예매)·refused 0 으로 실제 동시성을 확인했습니다.

**근거** — `docs/notes/K6_Port_Exhaustion_Troubleshooting.md`

### Q22. 833 TPS 는 어떤 환경에서 나온 숫자인가? 신뢰할 수 있나?

**모범 답변**
> i7-9700 8코어, 32GB 단일 머신의 Docker Desktop 에서 앱·MySQL(2코어)·Redis·k6 를 함께 돌린 값입니다. 부하 발생기와 서버가 CPU 를 나눠 쓰므로 **절대값보다 같은 환경에서의 Before/After 비교**에 의미를 둡니다. 그래서 모든 실험을 3회 반복해 일관성을 확인했고, 결과 문서에 환경 메타를 함께 남겼습니다. 운영 용량 산정에 쓰려면 분리된 환경에서 다시 측정해야 합니다.

### Q23. E2 는 왜 open-loop 로 측정했나?

**모범 답변**
> closed 모델(고정 VU 가 응답을 받고 다음 요청)은 서버가 느려지면 요청 속도도 같이 떨어져 붕괴가 가려집니다(coordinated omission). 실제 사용자는 서버가 느리다고 덜 오지 않으니, 도착률을 고정한 open-loop(RATE=500)로 측정했습니다. 그래서 입장 제어 off 에서 VU 가 2,000 까지 불어나고 38k 가 미처리되는 무경계 열화가 드러났습니다.

### Q24. 테스트는 어떻게 구성했나?

**모범 답변**
> 28개 테스트 클래스 중 통합 테스트 11개는 Testcontainers 로 실제 MySQL·Redis 를 띄웁니다. 정합성은 H2 같은 인메모리 DB 로 검증하지 않았습니다 — 생성 컬럼·유니크 제약·낙관락 충돌 동작이 MySQL 과 달라 통과해도 믿을 수 없기 때문입니다. 나머지는 컨트롤러 슬라이스·단위 테스트입니다. 테스트를 쓰기 전에 "이게 비즈니스 로직이나 설계 결정을 검증하는가"를 먼저 따져서 getter 나 프레임워크 동작 테스트는 만들지 않았습니다.

**⚠ 주의** — `build.gradle.kts` 에 `testRuntimeOnly("com.h2database:h2")` 가 남아 있지만 테스트 코드에서 쓰는 곳이 없다. "H2 안 썼다면서 의존성은 왜 있나"를 대비해 면접 전에 정리하거나, 남아 있는 이유를 확인해 둔다.

## 6. 운영 · 확장

### Q25. 인스턴스를 여러 개 띄우면 무엇이 깨지나?

**모범 답변**
> 상태는 전부 Redis·DB 에 있어서 앱은 무상태입니다. 스케줄러가 관건인데, 만료 sweep 은 건별 트랜잭션에서 상태를 재확인하므로 여러 인스턴스가 동시에 돌아도 중복 작업만 낭비될 뿐 정합성은 지켜집니다. reconcile 도 `SREM`/`SADD` 가 멱등이고 missing 복원은 grace 로 막아서 안전합니다. 다만 낭비를 줄이려면 ShedLock 같은 리더 선출을 붙이겠습니다.

**꼬리 질문 — ⚠ Redis Cluster 로 가면?**
> 선점 Lua 스크립트가 `avail:{id}` 와 `preempt:ts:{id}` 두 키를 함께 건드리는데, 지금 키에는 해시 태그가 없어 Cluster 에선 서로 다른 슬롯에 배치돼 CROSSSLOT 에러가 납니다. `avail:{1}`, `preempt:ts:{1}` 처럼 scheduleId 를 해시 태그로 감싸 같은 슬롯에 두면 됩니다. 스케줄 단위로 키가 나뉘어 있어 샤딩 자체는 자연스럽습니다.

### Q26. Redis 가 죽으면?

**모범 답변**
> 입장과 예매가 Redis 에 의존하므로 단일 장애점입니다. 운영이라면 Sentinel 이나 Cluster 로 가용성을 확보합니다. 중요한 건 failover 중에도 **정합성은 DB 가 지킨다**는 점입니다(Q7). Redis 가 틀리면 언더셀이나 409 가 늘 뿐 오버셀은 생기지 않고, 복구 후 reconcile 이 DB 기준으로 수렴시킵니다.

### Q27. HELD 만료를 polling 스케줄러로 처리한 이유는? 운영 중 문제는 없었나?

**모범 답변**
> keyspace notification 은 전달 보장이 없고, DB 가 SoT 라 DB 의 `expires_at` 기준으로 sweep 하는 게 맞다고 봤습니다. 운영 중 실제 문제도 두 번 있었습니다.
> 하나는 처리율입니다. L6 soak 에서 처음 설정(100건 / 30초 ≈ 초당 3건)이 만료 유입을 못 따라가 만료 잔재가 쌓였습니다. 측정으로 병목을 확인한 뒤 배치 1,000건·주기 2초로 바꾸고, 커밋 후 Redis 부수효과를 scheduleId 별 한 번의 `SADD`/`DECRBY` 로 묶어 왕복 수를 건수가 아니라 스케줄 수로 줄였습니다(T4-13).
> 다른 하나는 timezone 입니다. 정합성 감사 게이트가 만료 잔재 약 3,700건을 잡아냈는데, 오버셀이 아니라 앱 Clock(KST)과 DB 시각의 9시간 차이로 인한 오판이었습니다. 환경 timezone 을 KST 로 통일해 해결했습니다(B-1).

### Q28. Java 25 · Spring Boot 4 를 고른 이유는? 가상 스레드는 썼나?

**모범 답변**

## 7. AI 협업

### Q29. AI 로 만들었다면, 본인이 판단한 부분은 어디인가? AI 가 틀린 사례는?

**의도** — README 에 섹션이 있으니 반드시 나온다. 구체 사례 하나를 짚을 수 있는지.

**모범 답변(사례를 하나 골라 깊게)**
> 모든 작업은 세 개의 게이트(계획 승인 → 테스트 유효성 → 커밋 승인)를 거쳤습니다. 대표 사례는 1,000 동시 부하의 연결 거부입니다. "앱이나 Tomcat 설정 문제"라는 추정으로 끝내지 않고 가설별 격리 실험으로 Docker NAT 가 원인임을 규명했습니다(Q21). 또 만료 sweep 최적화는 "느릴 것 같다"가 아니라 soak 에서 병목이 측정될 때만 착수하도록 트리거 조건을 먼저 정했습니다(Q27).
> 반대로 놓친 것도 있습니다. README 에 "분산 락으로 경합 제어"라고 적혀 있었지만 실제 운영 경로엔 락이 없었습니다. 코드와 문서를 대조하다 발견해 정정했습니다. 문서도 코드처럼 검증 대상이라는 걸 배웠습니다.
